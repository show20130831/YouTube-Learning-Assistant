# Postmortem: first unattended day, cloud analysis failed twice (2026-10-08)

**Status:** resolved the same day. **Impact:** none for the reader: the 12:00 digest was sent on time with all
three new videos. **Times:** Asia/Taipei.

## Summary

On the first day the system ran unattended, the cloud analysis job (`daily_pipeline`, 11:00) failed, and a
manual rerun hung for about ten minutes. The two failures had different causes:

1. The job held a database transaction open while reading YouTube feeds over the network. The feeds failed
   and were retried for minutes, and Neon closed the idle transaction.
2. An LLM request never finished. OpenRouter answered `200` immediately and then streamed keep-alive
   whitespace while the model was busy, so the HTTP read timeout never fired.

Both were fixed and deployed by 11:38. The rerun summarised the remaining videos by 11:43, and the digest went
out at 12:00.

## Root causes

### 1. A transaction held open across network calls

`discover_videos` read the subscriptions inside a transaction and then called the feed fetcher for each channel
without ending it. Locally, feeds answer in milliseconds and the problem never showed. In the cloud, YouTube's
feeds failed for almost every request that day, and the retries (8 attempts, up to 10 s apart) kept the
transaction idle for minutes. Neon's pooler ends idle transactions, so the job died.

Contributing factor: SQLAlchemy reopens a transaction on the first attribute access to a loaded object. Ending
the transaction is not enough if code then reads `channel.youtube_channel_id` after a commit.

### 2. No overall deadline on LLM requests

The httpx read timeout limits the gap between bytes, not the total time. OpenRouter keeps the connection alive
with whitespace while the model is queued or generating, so a slow free model could hold the job forever.

## Resolution

- **Transactions:** every job now commits before any network request (feeds, captions, Data API, LLM) and
  copies the values it needs into plain variables first (commit `381556a`). A regression test runs the jobs against a
  real Postgres session with fake network adapters that record whether a transaction was open when they were
  called; it was confirmed to fail on the old code (`tests/test_no_open_transactions.py`).
- **LLM deadline:** the client reads the response as a stream and enforces a 180 s overall deadline, then raises
  `LLMTimeout` so the next model is tried (commit `94bbdcf`). The Modal job timeout went from 30 to 60 minutes
  so three timed-out models still fit.

## What went well

- The failure did not reach the reader: analysis and delivery are separate jobs, and the digest would have
  reported the failure if the rerun had not finished in time.
- Modal's failure email gave the first signal.
- Model fallback worked as designed once requests could time out.

## What went wrong

- The transaction bug was invisible locally, where feeds are fast. Tests used fakes that answered instantly.
- The hang gave no signal at all: no error, no log line, no failed status.
- Diagnosis relied on reading logs by hand; nothing recorded which models were tried or how they failed.

## Lessons

- **Test the slow path.** Fakes that answer instantly hide timing bugs; the regression test now checks the
  invariant (no open transaction during I/O) rather than the timing.
- **Every external call needs an overall deadline,** not only a per-read timeout.
- **A failure that makes no noise is the worst kind.** The follow-ups focus on making each failure produce a
  record, a status and, when the reader would be affected, an alert.
